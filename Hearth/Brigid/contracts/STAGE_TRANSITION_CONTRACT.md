# Stage Transition Contract

Status: Candidate
Authority: Operations

## Rule

A phase transition is prohibited until the infrastructure required by the next phase exists.

## Required Before Activation

- governing doctrine;
- operational standards;
- validation;
- deterministic recovery;
- implementation contracts;
- repository destinations.

Execution follows infrastructure.

Infrastructure precedes execution.

## Transition Evidence

Every phase transition must identify:

- completed phase;
- next phase;
- validated deliverables;
- unresolved blockers;
- queued refinements;
- active mission;
- active task;
- recovery state;
- governing commit.

## Failure Rule

If required infrastructure is missing, the transition remains blocked.

The repository must report the missing condition.

No phase is declared active through conversation alone.

## Mortar Requirements

Before transition, the next phase must have:

- defined inputs;
- defined outputs;
- stable identifiers;
- repository destinations;
- dependency map;
- validation criteria;
- failure conditions;
- recovery path;
- implementation queue;
- executable next task.

## Transition States

- `proposed`
- `prepared`
- `validated`
- `active`
- `complete`
- `blocked`

Only `validated` may transition to `active`.


## Construction Grammar

Every phase shall be prepared using this sequence:

1. Strike the Root.
2. Build Stout.
3. Lay Mortar.
4. Build Tools before Features.
5. Forge integrated capability.
6. Proceed with Molasses.
7. Seek More Birds.
8. Validate.
9. Transition.

A transition is evidence that preparation succeeded, not that implementation merely began.
