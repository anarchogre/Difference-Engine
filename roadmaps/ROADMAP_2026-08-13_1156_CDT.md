## 2. KALI CAPABILITY HARVEST — QUEUED

Kali Linux is treated as a **capability source and isolated security laboratory**, not as a replacement for the Forge operating system.

### Governing rule

**Do not add Kali repositories directly to the Forge Ubuntu package sources.**

Preferred acquisition order:

1. Identify the required capability, not the distribution.
2. Determine the exact upstream tool/package implementing it.
3. Prefer the Ubuntu/Debian-native or upstream-supported build where compatible.
4. Verify provenance, version, hashes/signatures where available, dependencies, license, and maintenance burden.
5. Package useful tools as dormant DE Capability Objects where practical.
6. Expose them to Pan only when the active task requires them.
7. Record tool purpose, scope constraints, invocation evidence, and removal/recovery path.
8. If compatibility or isolation requires Kali itself, use a bounded Kali VM/container/dedicated node rather than contaminating the Forge host.
9. Promote only validated capabilities.

## 3. KALI ISOLATION POLICY

If Kali itself becomes necessary:

Preferred order:

`tool cherry-pick → isolated container/VM → dedicated Kali node`

Only use a full Kali environment when:
- Kali-specific packaging materially reduces implementation burden,
- a tool's dependency graph is impractical on Ubuntu,
- hardware/security-lab isolation is useful,
- or a reproducible test image is itself valuable.

Any Kali environment should be:
- disposable/rebuildable
- versioned
- network-bounded where appropriate
- evidence-instrumented
- separated from durable DE authority/state
- recoverable from a documented bootstrap

Kali is an instrument, not authority.
